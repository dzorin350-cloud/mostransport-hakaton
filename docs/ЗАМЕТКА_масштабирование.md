# ЗАМЕТКА (набросок для обсуждения): горизонтальное масштабирование

> Это набросок, а не проверенная схема. В тестах запускался один экземпляр контейнера.

## Как устроено сейчас (один экземпляр)
- **API-воркеры** (uvicorn, по числу vCPU) не хранят состояния между запросами: прогноз в памяти — копия файла `state/forecast.parquet`, авторизация — JWT (проверка без обращения к базе).
- **Движок** (`engine/refresher.py`) — один фоновый процесс на контейнер: пересчитывает прогноз и публикует файл.
- **Состояние на диске:** история (`/app/history`), принятые данные (`/app/ingest`), пользователи (`/app/auth/users.db`), прогноз (`/app/state`).

## Что меняется при нескольких экземплярах

| Компонент | Сейчас | Для N экземпляров |
|---|---|---|
| API-воркеры | в каждом контейнере | без изменений: балансировщик (nginx / Kubernetes Service) раскидывает запросы, сессий нет |
| Токены JWT | секрет в файле тома | общий секрет из переменной `AUTH_SECRET` (секрет-хранилище), чтобы токен одного экземпляра принимали все |
| Пользователи | SQLite в томе | общая БД (PostgreSQL) — SQLite нельзя разделять между машинами |
| Принятые данные | CSV в томе `/app/ingest` | общее хранилище (S3 / ClickHouse) или очередь; иначе данные останутся в одном экземпляре |
| Пересчёт прогноза | в каждом контейнере | вынести в отдельный сервис (один на кластер), публиковать прогноз в общее хранилище (S3 / объектное хранилище), экземпляры API только читают; сейчас каждый экземпляр пересчитал бы сам — корректно, но избыточно (≈ 5–30 с CPU на пересчёт) |
| Внешние данные | каждый экземпляр скачивает сам | общий кэш (отдельный сервис или объектное хранилище) |

## Оценка
Один экземпляр 4 vCPU держит ~750–1 280 RPS (см. `docs/TESTS.md` §5), рост линейный по экземплярам,
пока узкое место — CPU API-воркеров (прогноз в памяти ~87 тыс. строк, ~0,9–1 ГБ RAM на экземпляр).
