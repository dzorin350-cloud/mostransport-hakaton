# Ограничения решения и план развития

## 1. Ограничения

| Ограничение | Что смягчает сейчас |
|---|---|
| **История маршрутов — 10 месяцев 2025 года**: годовая сезонность берётся по городу, а не по маршруту | многолетняя статистика data.mos.ru; форма дня «тот же месяц год назад»; точность на 7–8 мес. 0,85–0,89 |
| **Уровень на 2+ месяца неточен**: сезонный множитель между годами колеблется до ±5 % | коридор 80 % шире на дальнем горизонте; еженедельное обновление по фактам (октябрь 0,8952 → 0,9038) |
| **Внутридневная форма даёт ~9 % ошибки** | смесь CatBoost и свежего профиля; погода, календарь и события эту часть не объяснили |
| **Будущие перекрытия, ремонты, аварии, мероприятия модель не видит** | история очищена от таких дней; сценарный коэффициент |
| **Новый маршрут** требует 8+ недель данных и переобучения; **горизонт — до 12 месяцев** (рост зашит в множители, ≈ +11 %/год) | переобучение одной командой; вне горизонта — понятная ошибка API |
| **Погода** — только сильный дождь и только на 16 дней | как признак модели погода вредила; оставлена проверенная поправка −2,5 % |
| **Остановки — только оценка**: в валидациях нет привязки к остановке, телематики нет; валидация — вход, а не наполненность | разбивка по GTFS и окружению (OSM) подписана как оценка; основная величина — поток маршрута |
| **Нормы выпуска восстановлены по данным** (медиана вагонов с валидациями), порог переполнения — 90-й процентиль маршрута, а не паспортная вместимость | рекомендация подписана как оценка; на сен–окт совпала с потребностью (пик 676 против 674 вагоно-часов) |
| **Предупреждения о переполнении умеренно точные** (полнота 0,63, точность 0,45); эффект рекомендаций не доказан причинно | указывается уверенность; журнал решений копит данные для калибровки |
| **Сценарии, кроме дождя, — ручные гипотезы** и умножают все маршруты одинаково; перераспределения вагонов между маршрутами нет | измеренный эффект дождя применяется сам; сценарии — инструмент «что если» |
| **Пересчёт в контейнере API**: на 4–5 с p95 растёт до ≈ 1,4 с (ошибок нет) | пересчёт только при новых данных и раз в сутки; в остальное время p95 6–10 мс |
| **Приём данных — пакетами HTTP; один экземпляр; авторизация — прототип** (нет ролей, сброса пароля, аудита) | идемпотентный приём и автопересчёт; API без состояния, пользователи и журналы в PostgreSQL; JWT + PBKDF2 |
| **Демо-режим стенда**: «сегодня» — 01.11.2025, погода первых 16 дней — из архива; загрузка data.mos.ru из РФ не проверена | в проде `NOW_MODE=real`, `WEATHER_MODE=forecast`; источник → кэш → встроенная копия |

## 2. План развития (от окончания хакатона)

| Когда | Что |
|---|---|
| **Недели 1–2. Промышленный запуск** | валидации через Kafka (до подключения — ночная выгрузка в `/ingest`) с проверками качества; пересчёт в отдельном сервисе (убирает просадку p95); переобучение по расписанию с MLflow; мониторинг качества (§4); SSO с ролями «диспетчер», «планировщик», «администратор» и аудитом |
| **Недели 3–4. Точнее рекомендации** | план выпуска депо и паспортная вместимость вместо восстановленных норм; калибровка предупреждений по журналу решений (цель: точность и полнота ≥ 0,6); подтверждение исполнения из системы выпуска; перераспределение вагонов между маршрутами одного депо; плановые события Дептранса как сценарии на даты и маршруты |
| **Недели 5–6. Масштаб и детализация** | несколько экземпляров API за балансировщиком (один экземпляр 4 vCPU ≈ 1 150 RPS при p95 ≤ 300 мс, рост линейный); остановки по телематике (координаты вагона при валидации); пилот на автобусах |
| **Недели 7–10. ИИ-помощник диспетчера** | LLM с вызовом нашего API, развёрнутая в контуре заказчика; числа — только из API, решения — за диспетчером. Функции: сводка на смену (тип дня, погода, 3 окна риска, что изменилось, итоги вчера); объяснение рекомендации (причина, уверенность, что будет без действий); вопросы обычным языком («сколько вагонов на 17-м завтра к 8:00?», «что если концерт?»); черновик распоряжения в депо; сменный отчёт план / факт; разбор ошибок прогноза |
| **После 6–12 месяцев данных** | погода как признак модели (дождь в пик, снег, мороз); сезонность по каждому маршруту; модель на уровне остановок |

## 3. Обучение модели в проде

| Периодичность | Что |
|---|---|
| Непрерывно | валидации поступают, проверяются (полнота, дубли, провалы объёма) и агрегируются по часам |
| **Ежедневно, ночью** | пересчёт прогноза без переобучения: уровень (56 дней), профиль (2 недели), календарь, сезонность, погода; прошлая версия — в архив для контроля точности (работает уже сейчас) |
| **Еженедельно** | переобучение CatBoost на всей очищенной истории; выкладка только если на последних 8 неделях WAPE-score не хуже текущей модели более чем на 0,5 пункта и смещение в ±3 %; реестр MLflow, откат одной командой |
| **Ежемесячно** | подбор гиперпараметров и весов смеси (Optuna); пересчёт норм вагонов, порогов предупреждений и коридора |
| По сигналу мониторинга | внеплановое переобучение или пересмотр параметров |

## 4. Мониторинг и метрики

**Как считаем:** ночью каждый день факта сравнивается с прогнозом из архива, сделанным до него (`/monitor/accuracy`,
экран «Качество прогноза»), — по сети и маршрутам, по горизонтам 1–7, 8–30, 31–61 день.

| Техническая метрика | Норма | Сигнал |
|---|---|---|
| WAPE-score (7 и 28 дней) | ≥ 0,90 на неделю, ≥ 0,88 на 2 месяца | < 0,85 за 7 дней (алерт уже есть) |
| Смещение Σпрогноз / Σфакт − 1 | ±3 % | за ±5 % |
| Покрытие коридора 80 % | 75–85 % | вне 70–90 % |
| Предупреждения о переполнении | точность ≥ 0,45, полнота ≥ 0,6 | ниже за месяц |
| Данные | полные сутки к 3:00, объём ±30 % от нормы | неполные сутки, провал |
| Сервис | p95 ≤ 300 мс, 0 ошибок, прогноз не старше суток | нарушение |

**Если вне нормы:** 1) проверить данные (полнота, дубли, сбои валидаторов) → дозагрузить или исключить сбойные дни;
2) проверить события Дептранса → пометить дни в очистке, сценарий на время события; 3) деградация 2+ недели без причины →
внеплановое переобучение; 4) не помогло (новая трасса, объединение маршрутов) → пересмотр окон уровня и профиля, весов смеси,
Optuna; 5) коридор вне нормы → пересчёт по ошибкам 3 месяцев; 6) упала точность предупреждений → пересчёт норм и порогов.

**Бизнес-метрики решения:** часы переполнения (цель −20–30 % за квартал); вагоно-часы, перенесённые из межпика в пик без
роста выпуска (оценка ≈ 160 в день); доля принятых (> 60 %) и исполненных рекомендаций; время от рекомендации до решения
(< 15 мин для критичных); жалобы на переполненность; регулярность интервалов в пик.

**Метрики ИИ-помощника.** Технические: числа совпадают с API — 100 %; верные вызовы API на контрольных вопросах ≥ 95 %;
«не знаю» вместо выдумки вне области ≥ 95 %; ответ ≤ 10 с, сводка ≤ 30 с. Бизнес: время на подготовку сводки — с десятков
минут до нуля; сокращение времени от рекомендации до решения; ≥ 80 % ответов «полезно»; ≥ 90 % сводок открыто сменой.
