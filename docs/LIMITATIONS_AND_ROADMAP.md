# Ограничения решения, план развития и мониторинг в проде

Содержание: [1. Ограничения](#1-ограничения-текущего-решения) · [2. План развития](#2-план-развития-после-хакатона) · [3. Обучение модели в проде](#3-обучение-и-обновление-модели-в-проде) · [4. Мониторинг: метрики и действия](#4-мониторинг-качества-в-проде-метрики-и-действия)

## 1. Ограничения текущего решения

Для каждого ограничения: в чём оно, чем грозит на практике и что сейчас его смягчает.

### 1.1 Модель и данные
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Короткая история: 10 месяцев 2025 года** по маршрутам | годовая сезонность оценивается по городу в целом, а не по каждому маршруту; маршрут с особой сезонностью (например, к паркам летом) прогнозируется с городской формой года | сезонные множители по многолетней статистике data.mos.ru; годовая форма дня «тот же месяц год назад»; точность на 7–8 месяцев 0,85–0,89 |
| **Неопределённость уровня на 2+ месяца** | сезонный множитель между годами колеблется до ±5 %, это главная ошибка по сумме | коридор 80 % шире на дальнем горизонте; еженедельное обновление по новым фактам (октябрь: 0,8952 → 0,9038) |
| **Внутридневная форма даёт ~9 % ошибки** | почасовой прогноз конкретного часа менее точен, чем дневной итог | смесь CatBoost и свежего профиля; ни погода, ни календарь, ни события эту часть не объяснили |
| **Будущие перекрытия, ремонты, аварии и мероприятия модель не видит** | прогноз предполагает штатную работу маршрута; в дни событий ошибка большая | история очищается от таких дней; сценарный коэффициент задаёт поправку вручную |
| **Новый маршрут без истории** | CatBoost не знает маршрут | нужны 8+ недель валидаций и переобучение (`service/engine/train.py`) |
| **Горизонт не больше 12 месяцев** | дальше прогноз не строится; рост пассажиропотока зашит в сезонные множители (≈ +11 % за год по 2019–2025), при смене тренда годовой прогноз сместится | API возвращает понятную ошибку |
| **Погода — только на 16 дней и только сильный дождь** | снег, мороз, жара не учитываются; дальше двух недель погоды нет | эффект измерен: как признак модели погода вредила; оставлена проверенная поправка −2,5 % в сильный дождь |
| **Нет данных по остановкам** | в валидациях нет привязки к остановке, справочник не стыкуется с номерами маршрутов, телематики нет | разбивка по остановкам — оценка по расписанию GTFS и окружению (OpenStreetMap), подписана как оценка; основная величина — пассажиропоток маршрута |
| **Посадки ≠ пассажиры в вагоне** | валидация — это вход; выход и безбилетники не видны, наполненность вагона оценивается косвенно | загрузка считается как посадки на вагон относительно истории маршрута |

### 1.2 Диспетчерская логика
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Нормы выпуска восстановлены по данным**, а не взяты из плана депо: «обычно вагонов» — медиана вагонов с валидациями за 8 недель | рекомендация — оценка, а не утверждённое расписание | подписано в интерфейсе и API; на сен–окт рекомендация совпала с потребностью по факту (пик 676 против 674 вагоно-часов) |
| **Порог переполнения — из истории маршрута** (90-й процентиль посадок на вагон), а не паспортная вместимость | «риск» означает «необычно много для этого маршрута», а не физическую переполненность | предупреждение называется предупреждением, указывается уверенность |
| **Точность предупреждений о переполнении умеренная** (полнота 0,63, точность 0,45 на сен–окт) | примерно каждое второе срабатывание ложное | журнал решений копит данные для калибровки порогов |
| **Эффект рекомендаций не доказан причинно** | журнал показывает решения и факт посадок, но не подтверждает, что рекомендация была исполнена и помогла | отчёт по решениям с фактом; честная пометка в интерфейсе |
| **Сценарные коэффициенты — ручные гипотезы** (кроме дождя) | «Мероприятие», «Сбой сети» умножают весь прогноз одинаково на все маршруты и часы | измеренный эффект дождя применяется автоматически; остальное — инструмент «что если» для диспетчера |
| **Перераспределение вагонов между маршрутами не предлагается** | рекомендации только «добавить / снять» внутри маршрута | нужна привязка маршрутов к депо и паркам |

### 1.3 Сервис
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Пересчёт прогноза идёт в том же контейнере, что и API** | на ≈ 4–5 с счётной части p95 поднимается до ≈ 1,4 с (ошибок нет) | пересчёт только при новых данных и раз в сутки; вне пересчёта p95 6–10 мс |
| **Приём данных — пакетами через HTTP**, а не потоком | сервис ждёт полные дни; частота обновления — по мере загрузки | идемпотентный приём, защита от повторов и конфликтов, автоматический пересчёт |
| **Один экземпляр** | горизонтальное масштабирование описано, но не проверено | API без состояния, пользователи и журналы уже в общей PostgreSQL (см. §2, этап 3) |
| **Авторизация — прототип** | нет ролей, сброса пароля, ограничения попыток входа, аудита | JWT, PBKDF2, секреты задаются переменными окружения |
| **Демо-режим стенда** | «сегодня» — 01.11.2025, погода в первые 16 дней — из архива фактов (только для показа) | в проде `NOW_MODE=real`, `WEATHER_MODE=forecast`; в сабмите погода не используется |
| **Загрузка data.mos.ru из российской сети не проверена** (из-за рубежа сайт закрыт) | при сбое сезонность берётся из встроенной копии до октября 2025 | трёхуровневая схема «источник → кэш → встроенная копия», статус в `/model/info` |

## 2. План развития после хакатона

Сроки — от окончания хакатона. Этапы 1–3 укладываются в **два месяца** (недели 1–8), ИИ-помощник — **третий месяц**
(недели 9–12). Часть улучшений зависит не от разработки, а от накопления данных — они вынесены отдельно.

### Этап 1. Промышленный запуск — недели 1–3
1. **Поток данных:** валидации из системы оплаты проезда поступают в шину (Kafka) и агрегируются по часам на лету;
   до подключения шины — ночная выгрузка за сутки через `POST /ingest/validations`. Проверки качества на входе: полнота суток
   по маршрутам, дубликаты, резкие провалы объёма (сбой валидаторов).
2. **Отдельный сервис пересчёта:** движок выносится из контейнера API (убирает просадку p95 во время пересчёта), публикует
   версии прогноза в общее хранилище; экземпляры API только читают.
3. **Конвейер переобучения и реестр моделей** (MLflow) — см. §3: регулярное переобучение, проверка перед выкладкой, откат.
4. **Мониторинг качества** в проде — см. §4: технические и бизнес-метрики, пороги, действия.
5. **Промышленная авторизация:** корпоративный SSO (OAuth2 / OIDC), роли «диспетчер» (видит, принимает рекомендации),
   «планировщик» (утверждает план выпуска), «администратор»; аудит действий.

### Этап 2. Точнее рекомендации диспетчеру — недели 4–6
1. **Реальные нормы и вместимость:** план выпуска депо и паспортная вместимость типов вагонов вместо норм, восстановленных
   по данным, — «риск переполнения» становится физической величиной.
2. **Калибровка предупреждений** по журналу решений и фактам: пороги по маршрутам и часам; цель — точность выше 0,6 при
   полноте не ниже 0,6.
3. **Подтверждение исполнения:** связь с системой выпуска (сколько вагонов реально вышло) → оценка эффекта рекомендаций.
4. **Перераспределение между маршрутами одного депо:** «снять 2 вагона с маршрута 26 в межпик и отдать 17».
5. **Плановые события в прогнозе:** разбор объявлений Дептранса (ремонты, перекрытия, мероприятия) → сценарий на конкретные
   даты и маршруты вместо общего коэффициента.

### Этап 3. Масштаб и детализация — недели 7–8
1. **Горизонтальное масштабирование:** несколько экземпляров API за балансировщиком, общий секрет токенов, управляемая
   PostgreSQL с репликой. Один экземпляр 4 vCPU держит ≈ 1 150 RPS при p95 ≤ 300 мс, рост линейный по экземплярам.
2. **Остановки по телематике:** привязка валидаций к остановкам по координатам вагона в момент валидации → первая модель
   на уровне остановки и загрузка по перегонам (при доступе к данным телематики).
3. **Пилот на другом виде транспорта** (автобус / электробус) тем же конвейером при наличии почасовых валидаций.

### Этап 4. ИИ-помощник диспетчера — месяц 3 (недели 9–12)
LLM с вызовом инструментов поверх нашего API. Все числа помощник берёт только из API (прогноз, план, рекомендации,
точность) — сам ничего не придумывает; решения остаются за диспетчером. Модель — развёрнутая в контуре заказчика
(российская LLM или открытая модель), данные наружу не уходят.

| Функция | Что делает |
|---|---|
| **Утренняя сводка на смену** | к началу смены: тип дня (праздник, перенос), погода, 3 главных окна риска по маршрутам с рекомендацией выпуска, что изменилось в прогнозе со вчера, итоги вчерашнего дня (точность, принятые решения) |
| **Объяснение рекомендации** | почему риск: прогноз против нормы маршрута, коридор, причина (день недели, праздник, дождь, сценарий), уверенность, что будет, если ничего не делать |
| **Вопросы обычным языком** | «сколько вагонов нужно на 17-м завтра к 8:00?», «что будет, если вечером на Бауманской концерт?» → запросы к `/forecast`, `/plan`, `/alerts` со сценарием и ответ с цифрами |
| **Черновик распоряжения в депо** | по принятому плану выпуска — текст распоряжения; отправляет диспетчер после проверки |
| **Сменный отчёт** | план против факта, принятые и отклонённые рекомендации, где прогноз ошибся |
| **Разбор ошибок** | «почему вчера ошиблись на 25-м» — сопоставление с событиями (перекрытия, погода, сбои данных) |

### После накопления данных (6–12 месяцев эксплуатации)
- **Погода как признак модели:** почасовая поправка (дождь в час пик), снег и мороз — нужен год истории вместе с погодой.
- **Сезонность по каждому маршруту** — нужен полный год данных по маршрутам.
- **Модель на уровне остановок** — после накопления истории с привязкой к остановкам (этап 3).

## 3. Обучение и обновление модели в проде

| Периодичность | Что происходит | Как |
|---|---|---|
| **Постоянно / ежедневно** | поступают валидации за прошедшие сутки | шина (Kafka) или ночная выгрузка → проверки качества → почасовые агрегаты |
| **Ежедневно, ночью** | **пересчёт прогноза без переобучения:** обновляются уровень маршрута (56 дней), профиль последних 2 недель, календарь, сезонность, прогноз погоды; прошлый прогноз уходит в архив для контроля точности | движок сервиса, как сейчас (≈ 25 с); к утренней смене — свежий прогноз на 12 месяцев |
| **Ежемесячно** | **переобучение CatBoost** на всей истории с очисткой аномалий | автоматический запуск; проверка перед выкладкой: бэктест на последних 8 неделях — WAPE-score не ниже текущей модели более чем на 0,5 пункта и смещение в пределах ±3 %; модель регистрируется в MLflow, выкладка только после проверки, откат на прошлую версию одной командой |
| **Ежеквартально** | подбор гиперпараметров и весов смеси (Optuna) на свежих данных; пересчёт норм вагонов, порогов предупреждений и коэффициентов коридора | офлайн, с тем же порогом проверки |
| **Внепланово** | переобучение или пересмотр параметров по сигналу мониторинга (§4) | тот же конвейер |

Сейчас уже работает: ежедневный пересчёт при новых данных, архив версий, контроль точности. Добавляется: автоматическое
переобучение по расписанию, реестр моделей и проверка перед выкладкой.

## 4. Мониторинг качества в проде: метрики и действия

### 4.1 Технические метрики прогноза
Считаются ночным заданием: каждый день факта сравнивается с прогнозом из архива, сделанным **до** этого дня (как сейчас в
`/monitor/accuracy` и на экране «Качество прогноза»), — по сети и по маршрутам, раздельно по горизонту (1–7 дней, 8–30,
31–61 день).

| Метрика | Как считается | Норма | Сигнал |
|---|---|---|---|
| **WAPE-score** | 1 − Σ\|факт − прогноз\| / Σ факт; скользящие 7 и 28 дней | ≥ 0,90 на неделе вперёд, ≥ 0,88 на 2 месяца | < 0,85 за 7 дней (алерт в интерфейсе уже есть) |
| **Смещение** | Σ прогноз / Σ факт − 1 | в пределах ±3 % | за ±5 % за 7 дней |
| **Покрытие коридора 80 %** | доля часов, где факт внутри [lo, hi] | 75–85 % | вне 70–90 % за 28 дней |
| **Качество предупреждений** | точность и полнота «риска переполнения» против фактической загрузки | точность ≥ 0,45, полнота ≥ 0,6 (сейчас), цель — ≥ 0,6 / ≥ 0,6 | падение ниже текущего уровня за месяц |
| **Качество данных** | полнота суток по маршрутам, задержка поступления, объём к обычному | полные сутки к 3:00, объём ±30 % от нормы | неполные сутки, провал объёма |
| **Сервис** | p95 задержки, ошибки, время и успешность пересчёта, возраст прогноза | p95 ≤ 300 мс, 0 ошибок, прогноз не старше суток | нарушение любого |

### 4.2 Что делаем, если метрики вне нормы
1. **Проверить данные:** полнота суток, дубли, сбои валидаторов. Если причина в данных — дозагрузить или исключить сбойные
   дни из обучения; прогноз пересчитается сам.
2. **Проверить события:** перекрытия, ремонты, мероприятия (объявления Дептранса). Если причина — событие, пометить эти дни
   в очистке и задать сценарий на время события.
3. **Деградация 2+ недели без понятной причины** — внеплановое переобучение CatBoost на свежих данных с проверкой перед
   выкладкой (§3).
4. **Переобучение не помогает** (изменилось поведение: новая трасса, объединение маршрутов, новый маршрут) — пересмотр
   параметров: окно уровня (сейчас 56 дней), окно профиля, веса смеси, подбор Optuna на свежих данных.
5. **Коридор вне нормы** — пересчитать коэффициенты коридора по последним 3 месяцам ошибок.
6. **Упала точность предупреждений** — пересчитать нормы вагонов (8 недель) и пороги по журналу решений.

### 4.3 Бизнес-метрики решения
| Метрика | Что показывает | Цель |
|---|---|---|
| **Часы переполнения** | доля маршруто-часов, где посадок на вагон выше порога маршрута | снижение на 20–30 % за квартал |
| **Вагоно-часы, перенесённые из межпика в пик** | сколько выпуска перераспределено без новых вагонов (оценка по истории ≈ 160 в день) | рост без увеличения общего выпуска |
| **Доля принятых рекомендаций** и **доля исполненных** | доверие диспетчеров и реальное применение | > 60 % принятых |
| **Время реакции** | от появления рекомендации до решения | < 15 минут для критичных |
| **Жалобы на переполненность** | обращения пассажиров по маршрутам | снижение |
| **Регулярность интервалов в пик** | соблюдение интервалов при изменённом выпуске | не хуже текущей |

### 4.4 Метрики ИИ-помощника
| Тип | Метрика | Цель |
|---|---|---|
| Техническая | **Точность чисел**: доля ответов, где все числа совпадают с API | 100 % (проверка на наборе контрольных вопросов при каждом обновлении) |
| Техническая | **Правильность вызовов инструментов**: нужный эндпоинт и параметры на контрольных вопросах | ≥ 95 % |
| Техническая | **Отказ вне области**: «не знаю» вместо выдуманного ответа на вопросы, которых нет в данных | ≥ 95 % |
| Техническая | Время ответа | сводка ≤ 30 с, ответ на вопрос ≤ 10 с (p95) |
| Бизнес | Время на подготовку утренней сводки | с десятков минут до нуля |
| Бизнес | Время от рекомендации до решения с объяснением против без | сокращение |
| Бизнес | Оценка полезности диспетчерами («полезно / нет» на каждом ответе) | ≥ 80 % «полезно» |
| Бизнес | Доля сводок, открытых сменой | ≥ 90 % |
