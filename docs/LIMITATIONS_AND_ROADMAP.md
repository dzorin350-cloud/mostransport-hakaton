# Ограничения решения и план развития

## 1. Ограничения текущего решения

Для каждого ограничения: в чём оно, чем грозит на практике и что сейчас его смягчает.

### 1.1 Модель и данные
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Короткая история: 10 месяцев 2025 года** по маршрутам | годовая сезонность оценивается по городу в целом, а не по каждому маршруту; маршрут с особой сезонностью (например, к паркам летом) прогнозируется с городской формой года | сезонные множители по многолетней статистике data.mos.ru; годовая форма дня «тот же месяц год назад»; точность на 7–8 месяцев 0,85–0,89 |
| **Неопределённость уровня на 2+ месяца** | сезонный множитель между годами колеблется до ±5 %, это главная ошибка по сумме | коридор 80 % шире на дальнем горизонте; еженедельное обновление по новым фактам (октябрь: 0,8952 → 0,9038) |
| **Внутридневная форма даёт ~9 % ошибки** | почасовой прогноз конкретного часа менее точен, чем дневной итог | смесь CatBoost и свежего профиля; ни погода, ни календарь, ни события эту часть не объяснили |
| **Будущие перекрытия, ремонты, аварии и мероприятия модель не видит** | прогноз предполагает штатную работу маршрута; в дни событий ошибка большая | история очищается от таких дней; сценарный коэффициент задаёт поправку вручную |
| **Новый маршрут без истории** | CatBoost не знает маршрут | нужны 8+ недель валидаций и переобучение (`service/engine/train.py`) |
| **Горизонт не больше 12 месяцев** | дальше прогноз не строится; рост пассажиропотока зашит в сезонные множители (≈ +11 % за год по 2019–2025), при смене тренда годовой прогноз сместится | API возвращает понятную ошибку |
| **Погода — только на 16 дней и только сильный дождь** | снег, мороз, жара не учитываются; дальше двух недель погоды нет | эффект измерен: как признак модели погода вредила; оставлена проверенная поправка −2,5 % в сильный дождь |
| **Нет данных по остановкам** | в валидациях нет привязки к остановке, справочник не стыкуется с номерами маршрутов, телематики нет | разбивка по остановкам — оценка по расписанию GTFS и окружению (OpenStreetMap), подписана как оценка; основная величина — пассажиропоток маршрута |
| **Посадки ≠ пассажиры в вагоне** | валидация — это вход; выход и безбилетники не видны, наполненность вагона оценивается косвенно | загрузка считается как посадки на вагон относительно истории маршрута |

### 1.2 Диспетчерская логика
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Нормы выпуска восстановлены по данным**, а не взяты из плана депо: «обычно вагонов» — медиана вагонов с валидациями за 8 недель | рекомендация — оценка, а не утверждённое расписание | подписано в интерфейсе и API; на сен–окт рекомендация совпала с потребностью по факту (пик 676 против 674 вагоно-часов) |
| **Порог переполнения — из истории маршрута** (90-й процентиль посадок на вагон), а не паспортная вместимость | «риск» означает «необычно много для этого маршрута», а не физическую переполненность | предупреждение называется предупреждением, указывается уверенность |
| **Точность предупреждений о переполнении умеренная** (полнота 0,63, точность 0,45 на сен–окт) | примерно каждое второе срабатывание ложное | журнал решений копит данные для калибровки порогов |
| **Эффект рекомендаций не доказан причинно** | журнал показывает решения и факт посадок, но не подтверждает, что рекомендация была исполнена и помогла | отчёт по решениям с фактом; честная пометка в интерфейсе |
| **Сценарные коэффициенты — ручные гипотезы** (кроме дождя) | «Мероприятие», «Сбой сети» умножают весь прогноз одинаково на все маршруты и часы | измеренный эффект дождя применяется автоматически; остальное — инструмент «что если» для диспетчера |
| **Перераспределение вагонов между маршрутами не предлагается** | рекомендации только «добавить / снять» внутри маршрута | нужна привязка маршрутов к депо и паркам |

### 1.3 Сервис
| Ограничение | Последствие | Что смягчает сейчас |
|---|---|---|
| **Пересчёт прогноза идёт в том же контейнере, что и API** | на ≈ 4–5 с счётной части p95 поднимается до ≈ 1,4 с (ошибок нет) | пересчёт только при новых данных и раз в сутки; вне пересчёта p95 6–10 мс |
| **Приём данных — пакетами через HTTP**, а не потоком | сервис ждёт полные дни; частота обновления — по мере загрузки | идемпотентный приём, защита от повторов и конфликтов, автоматический пересчёт |
| **Один экземпляр** | горизонтальное масштабирование описано, но не проверено | API без состояния, пользователи и журналы уже в общей PostgreSQL (см. §2, этап 1) |
| **Авторизация — прототип** | нет ролей, сброса пароля, ограничения попыток входа, аудита | JWT, PBKDF2, секреты задаются переменными окружения |
| **Демо-режим стенда** | «сегодня» — 01.11.2025, погода в первые 16 дней — из архива фактов (только для показа) | в проде `NOW_MODE=real`, `WEATHER_MODE=forecast`; в сабмите погода не используется |
| **Загрузка data.mos.ru из российской сети не проверена** (из-за рубежа сайт закрыт) | при сбое сезонность берётся из встроенной копии до октября 2025 | трёхуровневая схема «источник → кэш → встроенная копия», статус в `/model/info` |

## 2. План развития после хакатона

Порядок — по ценности для диспетчера и по зависимости шагов друг от друга.

### Этап 1. Промышленная эксплуатация (1–2 месяца)
1. **Вынести пересчёт прогноза в отдельный сервис** (или ограничить ему процессор и потоки CatBoost) — убирает просадку p95 во
   время пересчёта. Прогноз публикуется в общее хранилище, экземпляры API только читают.
2. **Горизонтальное масштабирование:** несколько экземпляров API за балансировщиком (nginx / Kubernetes Service), общий секрет
   токенов `AUTH_SECRET`, управляемая PostgreSQL с репликой, принятые данные — в общем хранилище (S3 / ClickHouse).
   Один экземпляр 4 vCPU держит ≈ 1 150 RPS при p95 ≤ 300 мс, рост линейный по экземплярам.
3. **Потоковый приём:** валидации напрямую из шины (Kafka / NATS) вместо HTTP-пакетов, агрегация по часам на лету, пересчёт
   по завершении суток.
4. **Промышленная авторизация:** корпоративный SSO / ЕСИА (OAuth2 / OIDC), роли «диспетчер» (видит, принимает рекомендации),
   «планировщик» (утверждает план выпуска), «администратор»; аудит действий.
5. **Регулярное переобучение** по расписанию с проверкой на отложенном периоде перед выкладкой, реестр моделей (MLflow),
   автоматический откат при падении точности.

### Этап 2. Точнее рекомендации диспетчеру (2–4 месяца)
1. **Реальные нормы и вместимость:** план выпуска депо и паспортная вместимость типов вагонов вместо норм, восстановленных по
   данным, — «риск переполнения» станет физической величиной.
2. **Калибровка предупреждений** по журналу решений и фактам: пороги по маршрутам и часам, цель — точность выше 0,6 при той же
   полноте.
3. **Подтверждение исполнения:** связь с системой выпуска (сколько вагонов реально вышло) → причинная оценка эффекта рекомендаций.
4. **Перераспределение между маршрутами одного депо:** «снять 2 вагона с маршрута 26 в межпик и отдать 17» — нужна привязка
   маршрутов к паркам.
5. **Плановые события в прогнозе:** автоматический разбор объявлений Дептранса (ремонты, перекрытия, мероприятия) → сценарий
   на конкретные даты и маршруты вместо общего коэффициента.

### Этап 3. Детализация и новые данные (4–6 месяцев)
1. **Остановки и перегоны:** привязка валидаций к остановкам по телематике (координаты вагона в момент валидации) → модель на
   уровне остановки и загрузка по перегонам; сейчас — только оценка.
2. **Погода как признак модели** после накопления года истории: почасовая поправка (дождь в час пик), снег и мороз; источник —
   Росгидромет или Яндекс Погода по договору.
3. **Сезонность по маршрутам** после накопления полного года по каждому маршруту.
4. **Другие виды транспорта и города:** тот же конвейер для автобусов и электробусов при наличии почасовых валидаций и месячной
   статистики.

### Этап 4. ИИ-помощник диспетчера
LLM-помощник поверх API: утренняя сводка «что важно сегодня и что сделать», объяснение рекомендации человеческим языком,
ответы на вопросы «почему на 17-м завтра риск». Данные и решения остаются в сервисе, помощник только формулирует.
