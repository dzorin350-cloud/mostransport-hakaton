# Ограничения решения и план развития

**Коротко.** Главное ограничение — данные: 10 месяцев истории, нет привязки к остановкам и телематики, нет плана
выпуска депо. Поэтому план развития начинается с подключения данных, а модель затем регулярно переобучается и проверяется
на фактах.

## 1. Ограничения

### Данные
- Только почасовые агрегаты валидаций по 10 маршрутам за 10 месяцев 2025 года — нет многолетней истории по маршрутам,
  поэтому годовая сезонность берётся по городу (data.mos.ru) с поправкой на чувствительность маршрута, оценённой всего по 10 месяцам.
- Нет привязки валидаций к остановкам и нет телематики (координат вагонов) — прогноз по остановкам только оценочный
  (расписание GTFS + окружение по OpenStreetMap), проверить его точность нельзя.
- Нет плана выпуска депо и паспортной вместимости вагонов — нормы выпуска восстановлены по данным (медиана вагонов
  с валидациями за 8 недель), порог переполнения — 90-й процентиль посадок на вагон маршрута.
- Валидация — это вход, а не наполненность: выход и безбилетный проезд не видны.
- Погода — только прогноз осадков на 16 дней; истории погоды вместе с посадками мало для признака модели.

### Модель
- Уровень на 2+ месяца неточен: сезонный множитель между годами колеблется до ±5 % → смягчают коридор 80 % и
  еженедельное обновление по фактам (реальный октябрь: 0,8983 → 0,9075).
- Внутридневная форма даёт ~9 % ошибки — погода, календарь и события её не объяснили.
- Будущие перекрытия, ремонты, аварии, мероприятия модель не видит → задаются сценарным коэффициентом; история от них
  очищена.
- Новый маршрут требует 8+ недель данных и переобучения; горизонт — до 12 месяцев (рост зашит в множители,
  ≈ +11 % в год).
- Погода в модели — только поправка −2,5 % в дни сильного дождя (как признак погода ухудшала точность).

### Рекомендации диспетчеру
- Предупреждения о переполнении умеренно точные: полнота 0,63, точность 0,45 на сен–окт → указывается уверенность,
  журнал решений копит данные для калибровки.
- Эффект рекомендаций не доказан причинно: не видно, исполнена ли рекомендация.
- Сценарии, кроме дождя, — ручные гипотезы и умножают все маршруты и часы одинаково.
- Нет перераспределения вагонов между маршрутами (нужна привязка маршрутов к депо).

### Сервис
- Пересчёт прогноза в контейнере API: на 4–5 с p95 растёт до ≈ 1,4 с (ошибок нет); в остальное время p95 6–10 мс.
- Приём данных пакетами HTTP, а не потоком; один экземпляр (масштабирование описано, не проверено).
- Авторизация — прототип: нет ролей, сброса пароля, ограничения попыток, аудита.
- Стенд в демо-режиме: «сегодня» — 01.11.2025, погода первых 16 дней — из архива (в проде `NOW_MODE=real`,
  `WEATHER_MODE=forecast`).

## 2. План развития (от окончания хакатона)

Главное ограничение — данные, поэтому их подключаем **с первой недели**, а дальше они накапливаются и постепенно входят в модель.

**Недели 1–2. Подключение данных и промышленный запуск**
- Валидации по всем трамвайным маршрутам Москвы в реальном времени (Kafka), с проверками качества (полнота суток,
  дубли, провалы объёма).
- Телематика (координаты вагонов) — привязка валидаций к остановкам и перегонам.
- План и фактический выпуск депо, паспортная вместимость типов вагонов.
- Многолетняя история валидаций по маршрутам (если есть у заказчика) — сезонность по каждому маршруту.
- События Дептранса (ремонты, перекрытия, мероприятия), погода — архив и прогноз.
- Пересчёт прогноза выносится в отдельный сервис (убирает просадку p95); SSO с ролями «диспетчер», «планировщик»,
  «администратор» и аудитом.

**Недели 3–4. Обогащение данных и новые признаки**
- Проверка и очистка новых данных; каждый новый признак (сезонность маршрута, почасовая погода, события, остановки)
  проходит бэктест и входит в модель, только если улучшает WAPE-score.
- Первая модель на уровне остановок по телематике.
- Реальные нормы и вместимость вместо восстановленных → «риск переполнения» становится физической величиной.

**Недели 5–6. Расширение на все трамваи**
- Переобучение на всех трамвайных маршрутах Москвы; проверка точности по каждому.
- Несколько экземпляров API за балансировщиком (один экземпляр 4 vCPU держит ≈ 1 100–1 400 RPS при p95 ≤ 300 мс, рост линейный).
- Перераспределение вагонов между маршрутами одного депо; подтверждение исполнения рекомендаций из системы выпуска.

**Недели 7–8. Пилот в диспетчерской**
- Работа на реальных сменах; мониторинг метрик (§4).
- Калибровка предупреждений по журналу решений (цель: точность и полнота ≥ 0,6).
- Плановые события — сценарии на конкретные даты и маршруты; регулярное переобучение с MLflow.

**Недели 9–10. ИИ-помощник диспетчера**
- LLM с вызовом нашего API, развёрнутая в контуре заказчика; числа — только из API, решения — за диспетчером.
- Сводка на смену: тип дня, погода, 3 окна риска, что изменилось в прогнозе, итоги вчерашнего дня.
- Объяснение рекомендации: причина, уверенность, что будет без действий.
- Вопросы обычным языком: «сколько вагонов на 17-м завтра к 8:00?», «что если вечером концерт?».
- Черновик распоряжения в депо, сменный отчёт «план / факт», разбор ошибок прогноза.

**Дальше — эксплуатация:** наблюдаем метрики, переобучаем по расписанию, добавляем признаки по мере накопления данных,
переносим подход на автобусы и электробусы.

## 3. Обучение модели в проде
- Непрерывно: валидации поступают, проверяются и агрегируются по часам.
- Ежедневно ночью: пересчёт прогноза без переобучения — уровень (56 дней), профиль (4 недели), календарь, сезонность,
  погода; прошлая версия уходит в архив для контроля точности (работает уже сейчас).
- Еженедельно: переобучение CatBoost; выкладка, только если на последних 8 неделях WAPE-score не хуже текущей модели
  более чем на 0,5 пункта и смещение в пределах ±3 %; реестр MLflow, откат одной командой.
- Ежемесячно: подбор гиперпараметров и весов смеси (Optuna); пересчёт норм вагонов, порогов предупреждений, коридора.
- По сигналу мониторинга: внеплановое переобучение или пересмотр параметров.

## 4. Мониторинг и метрики

**Как считаем:** каждую ночь каждый день факта сравнивается с прогнозом из архива, сделанным до него
(`/monitor/accuracy`, экран «Качество прогноза»), — по сети, маршрутам и горизонтам 1–7, 8–30, 31–61 день.

**Технические метрики (норма → сигнал):**
- WAPE-score за 7 и 28 дней: ≥ 0,90 на неделю вперёд, ≥ 0,88 на 2 месяца → сигнал ниже 0,85 за 7 дней
  (алерт в интерфейсе уже есть).
- Смещение Σпрогноз / Σфакт − 1: в пределах ±3 % → сигнал за ±5 %.
- Покрытие коридора 80 %: 75–85 % часов → сигнал вне 70–90 %.
- Предупреждения о переполнении: точность ≥ 0,45, полнота ≥ 0,6 → сигнал при падении за месяц.
- Данные: полные сутки к 3:00, объём в пределах ±30 % от нормы → сигнал при неполных сутках или провале.
- Сервис: p95 ≤ 300 мс, 0 ошибок, прогноз не старше суток.

**Если метрика вне нормы:**
1. Проверить данные (полнота, дубли, сбои валидаторов) → дозагрузить или исключить сбойные дни.
2. Проверить события (перекрытия, ремонты) → пометить дни в очистке, задать сценарий на время события.
3. Деградация 2+ недели без причины → внеплановое переобучение.
4. Не помогло (новая трасса, объединение маршрутов) → пересмотр окон уровня и профиля, весов смеси, подбор Optuna.
5. Коридор вне нормы → пересчёт по ошибкам последних 3 месяцев.
6. Упала точность предупреждений → пересчёт норм вагонов и порогов.

**Бизнес-метрики решения:**
- Часы переполнения — доля маршруто-часов выше порога загрузки: цель −20–30 % за квартал.
- Вагоно-часы, перенесённые из межпика в пик без роста общего выпуска (оценка по истории ≈ 160 в день).
- Доля принятых рекомендаций (> 60 %) и доля исполненных.
- Время реакции от рекомендации до решения: < 15 минут для критичных.
- Жалобы пассажиров на переполненность — снижение.
- Регулярность интервалов в пик — не хуже текущей.

**Метрики ИИ-помощника:**
- Технические: числа совпадают с API — 100 %; верные запросы к API на контрольных вопросах — ≥ 95 %; «не знаю» вместо
  выдумки вне области — ≥ 95 %; ответ ≤ 10 с, сводка ≤ 30 с.
- Бизнес: время подготовки сводки — с десятков минут до нуля; сокращение времени от рекомендации до решения;
  ≥ 80 % ответов «полезно»; ≥ 90 % сводок открыто сменой.
