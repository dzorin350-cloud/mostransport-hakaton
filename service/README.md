# Веб-сервис: прогноз пассажиропотока трамваев Москвы

Backend + frontend поверх ML-модели v7 (WAPE-score 0.88399, см.
[../ARCHITECTURE.md](../ARCHITECTURE.md) и [../README.md](../README.md)).

Этот каталог закрывает требования ТЗ хакатона, которых не было в исходной
модели: REST/HTTP API, интерактивный дашборд с картой, экспорт в
CSV/XLSX, корректирующие коэффициенты в интерфейсе, замеры
производительности.

**Рабочее место диспетчера:** после входа нажмите «Рабочее место диспетчера»
или откройте `http://localhost:8080/dispatcher.html`. Там есть сводка
«сейчас», алерты с действием и журналом решений, сценарий изменения спроса,
план выпуска на 1–7 дней с XLSX и проверка точности после поступления фактов.
Рекомендация вагонов — оценка по посадкам на вагон, не измерение наполненности.

Сервис сам применяет модель v7 к истории валидаций и сам скачивает внешние данные
(календарь isdayoff.ru, сезонность data.mos.ru); готовых CSV-прогнозов нет.
Устройство движка — [`engine/README.md`](engine/README.md), все прогоны и тесты — [`../docs/TESTS.md`](../docs/TESTS.md).

## Быстрый старт

```bash
cd service
docker compose up -d --build            # 4 vCPU / 4 ГБ RAM, 4 воркера (по умолчанию)
# минимальная конфигурация по ТЗ — 2 vCPU / 2 ГБ RAM, 2 воркера:
docker compose -f docker-compose.yml -f docker-compose.2cpu.yml up -d --build
```

- Дашборд: http://localhost:8080
- API: http://localhost:8123 (или http://localhost:8080/api/... через прокси nginx)
- Проверка: `curl http://localhost:8123/health`

Остановить: `docker compose down`.

## Архитектура

```
                 ┌── isdayoff.ru (календарь)        ┌─────────────────────────────┐
                 ├── data.mos.ru (сезонность)       │ api (один контейнер)          │
история          ▼                                   │                               │
валидаций ──► engine/refresher.py ──► state/versions/<id> + current.json ──► uvicorn-воркеры (FastAPI) ──► web (nginx, дашборд)
(HISTORY_DIR)  применяет 5 CatBoost,    + info.json   │  прогноз в памяти, горячая   │
               пересчёт при новых данных               │  перезагрузка новых версий   │
               и раз в REFRESH_HOURS                   └─────────────────────────────┘
```

**Кто считает прогноз.** Фоновый процесс в контейнере (`engine/refresher.py`) загружает 5 обученных
моделей CatBoost (обучаются офлайн, `engine/train.py`, код v7), читает историю валидаций, сам скачивает
внешние данные, чистит историю, считает уровни и профиль и строит почасовой прогноз на 12 месяцев вперёд от
даты последних данных. Пересчёт — при старте, при появлении новых файлов истории и по расписанию.
Таблица и её метаданные публикуются одной неизменяемой версией; каталог `state`
сохраняется в Docker volume. `runner.py` завершает контейнер, если фоновый
движок или API неожиданно остановился; Compose перезапускает его.

**Почему запросы не запускают модель.** ТЗ требует сотни RPS при p95 < 200–300 мс на 2–4 vCPU. Прогноз
меняется только при пересчёте, поэтому воркеры API держат готовую таблицу в памяти и отдают срезы
(двоичный поиск по дате): 1 282 RPS / p95 68 мс на 4 vCPU, 890 RPS на 2 vCPU.

Корректирующие коэффициенты (погода/событие/сезон) применяются
**множителем поверх готового прогноза** — мультипликативная структура
модели (`уровень × форма дня × сезонный множитель`, см. ARCHITECTURE.md
§1) прямо это позволяет, без повторного инференса.

## API

Данные отдаются только авторизованным пользователям (прототип: OAuth2 Password Flow, токен JWT, пользователи в PostgreSQL,
контейнер `db`). Без токена открыты `/health`, `/metrics`, `/docs`. Ошибки возвращаются с понятными сообщениями на русском.

| Эндпоинт | Что делает |
|---|---|
| `POST /auth/register` | регистрация: `{"username": ..., "password": ...}` |
| `POST /auth/token` | вход (форма `username`, `password`) → `access_token`; дальше заголовок `Authorization: Bearer <токен>` |
| `GET /auth/me` | текущий пользователь |
| `GET /now` | «что сейчас»: текущий час пользователя и 3 следующих по маршрутам (прогноз, коридор, загрузка, вагоны), итоги дня; на стенде — демо-дата |
| `GET /alerts` | предупреждения для диспетчера: переполнение, повышенная загрузка, избыток вагонов, праздники и переносы, погода, устаревшие данные, сбой пересчёта, падение точности |
| `GET /fleet` | загрузка вагонов по часам и рекомендация выпуска (`min_share` — минимальная доля обычного выпуска) |
| `GET /monitor/accuracy` | точность прогноза на поступивших фактах (архив прогнозов, `forecast=latest\|earliest`) |
| `GET /stops` | остановки маршрутов (GeoJSON) для карты |
| `GET /forecast/stops` | прогноз по остановкам за период (**оценочная** разбивка прогноза маршрута по расписанию GTFS) |
| `POST /ingest/validations` | сырые валидации в формате `train.csv` (CSV, «;»), сервис агрегирует по маршруту и часу |
| `POST /ingest/hourly` | почасовые посадки CSV `route;date;hour;boardings` |
| `GET /health` | статус сервиса |
| `GET /ready` | готовность: последний пересчёт успешен; используется Docker healthcheck |
| `GET /metrics` | счётчики запросов, средняя латентность, версия модели, дата данных |
| `GET /model/info` | как построен прогноз: дата данных, горизонт, множители месяцев, месяцы с годовой формой дня, источники внешних данных (`live` / `cache` / `fallback`), время расчёта |
| `GET /routes` | список маршрутов |
| `GET /routes/geometry` | GeoJSON геометрии 9 маршрутов (OpenStreetMap) |
| `GET /forecast` | прогноз с фильтрами: `date_from`, `date_to`, `route[]`, `hour_from/to`, `granularity=hour\|day\|week\|month`, `coefficient` |
| `GET /forecast/export` | то же самое, отдаёт файл `fmt=csv\|xlsx` |
| `GET /plan`, `GET /plan/export` | план выпуска вагонов на 1–7 дней, итог в вагоно-часах, XLSX для депо |
| `POST /decisions`, `GET /decisions` | журнал «принять / отклонить / отложить» по алертам |
| `GET /decisions/report` | решения и поступившее число посадок по дате и маршруту; не доказательство исполнения плана |

Приём данных: только даты после текущей даты данных; файлы сохраняются в том `ingest`, движок подхватывает их за ~1 минуту
и сдвигает горизонт.
Максимум 10 МБ на запрос; точный повтор пакета идемпотентен, пересекающиеся
маршрут-дата-час отклоняются, нечисловые и неизвестные маршруты отклоняются.
Отправитель должен передавать **полные дни**: сервис не может определить по
редкому потоку валидаций, что день ещё не завершён.

Пользователи, журнал решений диспетчера и журнал приёма данных хранятся в PostgreSQL
(контейнер `db` в `docker-compose.yml`, том `postgres`, подключение — `DATABASE_URL`).
Пароль базы по умолчанию — только для локального демо; перед внешним развёртыванием
задать `TRAM_DB_PASSWORD` и `AUTH_SECRET`. Прогноз и архив остаются Parquet на томе
`state` — БД не нужна на горячем пути чтения прогноза.

Пример (полный сценарий с авторизацией — [`../docs/JURY.md`](../docs/JURY.md)):

```bash
curl -H "Authorization: Bearer $TOKEN" "http://localhost:8123/forecast?date_from=2025-11-01&date_to=2025-11-07&route=17&granularity=day&coefficient=1.1"
```

Горизонт — 12 месяцев от даты последних данных (сейчас 01.11.2025 – 31.10.2026); запрос вне горизонта
получает 400 с понятным сообщением. В ответе `/forecast` есть `data_until` и `model_version`.
Ноябрь–декабрь 2025 совпадает с сабмитом v7 (0.88399) до 0,0023 %.

Полная интерактивная документация (Swagger UI): http://localhost:8123/docs.

## Дашборд

- **Карта** (MapLibre GL, тайлы OpenStreetMap без API-ключа): реальная
  геометрия 9 маршрутов, полученная через Overpass API
  (`relation[route=tram][ref=...]` по каждому маршруту, лицензия
  ODbL/CC-BY-SA). Цвет линии — относительная загрузка маршрута за
  выбранный период (зелёный/жёлтый/красный).
- **Три горизонта** (кнопки День / Месяц / Год) — критерий ТЗ п.4.
- **Фильтр по маршрутам** — клик по чипу слева.
- **Корректирующие коэффициенты**: слайдер ×0.5…×1.5 плюс пресеты
  «Дождь» (×0.85) / «Событие» (×1.15) / «Норма» — критерий ТЗ п.2в,
  результат виден мгновенно без перезагрузки страницы.
- **Экспорт CSV/XLSX** — кнопки внизу правой панели.
- KPI: сумма посадок за период, число активных маршрутов, пиковый час/день,
  latency p95 из нагрузочного теста (4 vCPU / 4 воркера).

Геометрия справочника `Хакатон_справочники_трамвай_10_маршрутов.xlsx`
(`Порядок_с_координатами`) для карты **не использована**: `route_id` в
нём — внутренняя нумерация парка подвижного состава, не совпадающая с
`ngpt_route` из train.csv/test.csv (проверено построчно: в справочнике
`route_short_name="5"` — это маршрут Рижская—Белорусский вокзал, тогда
как в данных валидаций маршрут 5 пуст). Прямой связки между двумя
системами нумерации в датасете нет, поэтому для карты взята независимая
и верифицируемая геометрия из OpenStreetMap по номеру маршрута.

## Производительность

Полные таблицы всех прогонов — [`../docs/TESTS.md`](../docs/TESTS.md) §5.

**Текущая ветка, смешанный профиль диспетчера, 60 с:**

| Лимит | Пользователей | RPS | p95 | CPU от лимита | RAM | Swap | Ошибки |
|---|---:|---:|---:|---:|---:|---:|---:|
| 2 vCPU / 2 ГБ | 100 | 174 | 110 мс | ≈ 73 % | ≈ 554 МиБ | 0 | 0 |
| 4 vCPU / 4 ГБ | 210 | 361 | 110 мс | ≈ 64 % | ≈ 923 МиБ | 0 | 0 |
| **4 vCPU / 4 ГБ, 10 минут** | **210** | **395** | **72 мс** | **≈ 60–64 %** | **≈ 930 МиБ** | **0** | **0 / ≈ 236 тыс.** |

Профиль включает план, алерты, остановки, мониторинг и частую выгрузку XLSX;
старые цифры ниже относятся к более лёгкому профилю прогноза и не должны
выдаваться за производительность всего продукта. После первого замера смешанного
профиля (72 RPS, p95 3 с) ответы плана, алертов, остановок и XLSX стали
кэшироваться по версии прогноза; на тех же 145 пользователях стало 240 RPS,
p95 190 мс. Стенд — Windows / AMD Ryzen 5 7530U, Docker Desktop и Locust
на одной машине. В 10-минутном прогоне p99 150 мс, память стабильна;
одновременный приём фактов под этой нагрузкой отдельно не проверялся.
Опциональный PostgreSQL после прогрева: 356 RPS, p95 130 мс, 0 ошибок
(4 vCPU API, 210 пользователей, 60 с); первый холодный прогон — 319 RPS,
p95 370 мс. БД работает отдельным контейнером, поэтому её ресурсы не входят
в лимит API-контейнера.

**Итог (с авторизацией, 4 vCPU / 4 ГБ, 4 воркера, 0 ошибок):**

Число воркеров uvicorn равно числу vCPU (переменная `WORKERS`). Замеры — `api/loadtest.py` (Locust):

```bash

```

Стенд: MacBook Air (Apple M5), Docker Desktop, Locust на той же машине; 30 с на прогон.

Прежний бэкенд (готовые CSV, до появления движка) — для сравнения:

| Конфигурация контейнера | Пользователей | RPS | p50, мс | p95, мс | p99, мс | CPU контейнера | Память |
|---|---|---|---|---|---|---|---|
| 2 vCPU / 2 ГБ, 2 воркера | 100 | 598 | 21 | 90 | 130 | — | — |
| 2 vCPU / 2 ГБ, 2 воркера | 200 | ≈ 610 | 160 | 280 | 330 | 195 % из 200 % | 310 МБ |
| 4 vCPU / 4 ГБ, 2 воркера | 200 | 689 | 140 | 250 | 340 | 220 % из 400 % | 302 МБ |
| 4 vCPU / 4 ГБ, 4 воркера | 200 | ≈ 885 | 77 | 190 | 250 | 404 % из 400 % | 521 МБ |
| 4 vCPU / 4 ГБ, 4 воркера | 400 | 879 | 280 | 440 | 520 | 405 % из 400 % | 582 МБ |

Выводы:

- **Потолок упирается в процессор:** при 4 воркерах CPU контейнера 404 % из 400 %, удвоение
  нагрузки (400 пользователей) не увеличивает RPS (≈ 880), растёт только задержка.
- **Лимит vCPU без увеличения воркеров ничего не даёт:** при лимите 4 vCPU и 2 воркерах RPS
  вырос лишь с 610 до 689, потому что 2 воркера используют около 2,2 ядра.
- Оба режима укладываются в требование ТЗ (сотни RPS, p95 < 200–300 мс на 2–4 vCPU).
- Движок хранит прогноз на 12 месяцев (87 600 строк); срез по дате двоичным поиском сделал его быстрее
  прежнего бэкенда на CSV (1 282 против 885 RPS на 4 vCPU).

Отчёты Locust: [`api/loadtest_report/`](api/loadtest_report/) — `loadtest_engine_*` (движок), `loadtest_<vCPU>_<воркеры>_*` (прежний бэкенд).
Профиль нагрузки — смесь запросов: почасовой прогноз на 1 маршрут/1 день (основной
паттерн дашборда), суточная агрегация на весь горизонт, запросы с
коэффициентом, health-check.

**На single-worker (без `--workers`)** тот же тест давал p95 690 мс —
цифра из первого прогона, оставлена для сравнения при отладке: узкое
место — GIL при синхронном pandas-фильтре, снимается несколькими
воркерами uvicorn (по числу vCPU, переменная `WORKERS` в Dockerfile).

## Область применимости (дополнение к ARCHITECTURE.md §8)

- Сервис применяет модель, но не переобучает CatBoost (это офлайн, `engine/train.py`),
  и не валидирует бизнес-осмысленность коэффициента (например, `×3.0`
  физически бессмысленно, но API его не отклонит за пределами диапазона
  `(0, 3]`, заданного как защита от опечатки, не как доменное ограничение).
- Геометрия карты — база OSM на момент выгрузки (сентябрь 2026); при
  изменении трассы маршрута в реальности карта не обновится без повторного
  запроса к Overpass API.
- Для прогноза за пределами ноября 2025 — октября 2026 нужен новый прогон
  `v7/code/forecast.py` с расширенным горизонтом (ограничение модели: до
  12 месяцев от конца обучающих данных, см. ARCHITECTURE.md §6).
