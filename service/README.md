# Веб-сервис: прогноз пассажиропотока трамваев Москвы и рабочее место диспетчера

Backend + frontend поверх итоговой ML-модели (WAPE-score 0,88960): движок сам применяет модель к истории валидаций и сам
скачивает внешние данные (календарь isdayoff.ru, сезонность data.mos.ru, прогноз осадков Open-Meteo), API отдаёт прогноз
и диспетчерские функции, интерфейс — рабочее место диспетчера. Инструкция для жюри — [`../docs/JURY.md`](../docs/JURY.md),
архитектура — [`../ARCHITECTURE.md`](../ARCHITECTURE.md), устройство движка — [`engine/README.md`](engine/README.md).

## ML-модель: артефакты, код обучения и инференса

**Итоговая модель — WAPE-score 0,88960 на лидерборде.** Прогноз = уровень маршрута (посадки в сутки за 56 дней) ×
форма дня (10 моделей CatBoost — базовые и с длиной светового дня — в смеси с профилем последних 4 недель) × сезонный множитель месяца (data.mos.ru, свой для маршрута);
обучение на истории, очищенной от перекрытий и сбоев. Подробно — [`../docs/MODEL.md`](../docs/MODEL.md), [`../ARCHITECTURE.md`](../ARCHITECTURE.md) §2.

| Что | Где |
|---|---|
| **Артефакты модели** | [`engine/artifacts/`](engine/artifacts/) — 10 моделей CatBoost `catboost_seed0…4.cbm` и `catboost_daylen_seed0…4.cbm`, `config.json` (параметры, дата обучения), нормы вагонов, коэффициенты коридора, остановки |
| **Код обучения** | [`../model/code/`](../model/code/) — сетка из `labels/`, очистка, признаки, CatBoost, профиль, сезонность, гиперпараметры Optuna; [`engine/train.py`](engine/train.py) — обучение моделей для сервиса |
| **Код инференса** | [`engine/core.py`](engine/core.py) — применение модели к истории; [`engine/sources.py`](engine/sources.py) — внешние данные; [`engine/refresher.py`](engine/refresher.py) — пересчёт и публикация; пакетный прогноз без сервиса — [`../model/code/forecast.py`](../model/code/forecast.py) |
| **Отправленный сабмит** | [`../model/submission.csv`](../model/submission.csv) и md5 |

```bash
# воспроизвести сабмит байт в байт (из корня репозитория)
cd model/code && python build_grid.py && python final.py && md5sum ../output/submission.csv   # = model/submission.md5
# прогноз на любой период до 12 месяцев
python forecast.py --start 2025-11-01 --end 2026-10-31 --out ../output/forecast.csv
# то же в Docker (из корня): docker build -t tram-model . && docker run --rm tram-model
# переобучить модели сервиса (из корня): python -m service.engine.train, затем docker compose up -d --build
```

Проверка: бэктест сен–окт 0,8776; реальный октябрь в сервисе — 0,9052 с еженедельными обновлениями; сервис против
сабмита на ноябре–декабре — расхождение 0,0043 %.

## Быстрый старт

```bash
cd service
docker compose up -d --build            # 4 vCPU / 4 ГБ RAM, 4 воркера (по умолчанию)
# минимальная конфигурация по ТЗ — 2 vCPU / 2 ГБ RAM, 2 воркера:
docker compose -f docker-compose.yml -f docker-compose.2cpu.yml up -d --build
```

- Дашборд: http://localhost:8080
- API: http://localhost:8123 (или http://localhost:8080/api/... через прокси nginx)
- Проверка: `curl http://localhost:8123/health`

Остановить: `docker compose down`.

## Архитектура

```
                 ┌── isdayoff.ru (календарь)        ┌─────────────────────────────┐
                 ├── data.mos.ru (сезонность)       │ api (один контейнер)          │
история          ▼                                   │                               │
валидаций ──► engine/refresher.py ──► state/versions/<id> + current.json ──► uvicorn-воркеры (FastAPI) ──► web (nginx, дашборд)
(HISTORY_DIR)  применяет 5 CatBoost,    + info.json   │  прогноз в памяти, горячая   │
               пересчёт при новых данных               │  перезагрузка новых версий   │
               и раз в REFRESH_HOURS                   └─────────────────────────────┘
```

**Кто считает прогноз.** Фоновый процесс в контейнере (`engine/refresher.py`) загружает 5 обученных
моделей CatBoost (обучаются офлайн, `engine/train.py`, код итоговой модели), читает историю валидаций, сам скачивает
внешние данные, чистит историю, считает уровни и профиль и строит почасовой прогноз на 12 месяцев вперёд от
даты последних данных. Пересчёт — при старте, при появлении новых файлов истории и по расписанию.
Таблица и её метаданные публикуются одной неизменяемой версией; каталог `state`
сохраняется в Docker volume. `runner.py` завершает контейнер, если фоновый
движок или API неожиданно остановился; Compose перезапускает его.

**Почему запросы не запускают модель.** ТЗ требует сотни RPS при p95 < 200–300 мс на 2–4 vCPU. Прогноз
меняется только при пересчёте, поэтому воркеры API держат готовую таблицу в памяти и отдают срезы
(двоичный поиск по дате): 1 282 RPS / p95 68 мс на 4 vCPU, 890 RPS на 2 vCPU.

Корректирующие коэффициенты (погода/событие/сезон) применяются
**множителем поверх готового прогноза** — мультипликативная структура
модели (`уровень × форма дня × сезонный множитель`, см. ARCHITECTURE.md
§1) прямо это позволяет, без повторного инференса.

## API

Данные отдаются только авторизованным пользователям (прототип: OAuth2 Password Flow, токен JWT, пользователи в PostgreSQL,
контейнер `db`). Без токена открыты `/health`, `/metrics`, `/docs`. Ошибки возвращаются с понятными сообщениями на русском.

| Эндпоинт | Что делает |
|---|---|
| `POST /auth/register` | регистрация: `{"username": ..., "password": ...}` |
| `POST /auth/token` | вход (форма `username`, `password`) → `access_token`; дальше заголовок `Authorization: Bearer <токен>` |
| `GET /auth/me` | текущий пользователь |
| `GET /now` | «что сейчас»: текущий час пользователя и 3 следующих по маршрутам (прогноз, коридор, загрузка, вагоны), итоги дня; на стенде — демо-дата |
| `GET /alerts` | предупреждения для диспетчера: переполнение, повышенная загрузка, избыток вагонов, праздники и переносы, погода, устаревшие данные, сбой пересчёта, падение точности |
| `GET /fleet` | загрузка вагонов по часам и рекомендация выпуска (`min_share` — минимальная доля обычного выпуска) |
| `GET /monitor/accuracy` | точность прогноза на поступивших фактах (архив прогнозов, `forecast=latest\|earliest`) |
| `GET /stops` | остановки маршрутов (GeoJSON) для карты |
| `GET /forecast/stops` | прогноз по остановкам за период (**оценочная** разбивка прогноза маршрута по расписанию GTFS) |
| `POST /ingest/validations` | сырые валидации в формате `train.csv` (CSV, «;»), сервис агрегирует по маршруту и часу |
| `POST /ingest/hourly` | почасовые посадки CSV `route;date;hour;boardings` |
| `GET /health` | статус сервиса |
| `GET /ready` | готовность: последний пересчёт успешен; используется Docker healthcheck |
| `GET /metrics` | счётчики запросов, средняя латентность, версия модели, дата данных |
| `GET /model/info` | как построен прогноз: дата данных, горизонт, множители месяцев, месяцы с годовой формой дня, источники внешних данных (`live` / `cache` / `fallback`), время расчёта |
| `GET /routes` | список маршрутов |
| `GET /routes/geometry` | GeoJSON геометрии 9 маршрутов (OpenStreetMap) |
| `GET /forecast` | прогноз с фильтрами: `date_from`, `date_to`, `route[]`, `hour_from/to`, `granularity=hour\|day\|week\|month`, `coefficient` |
| `GET /forecast/export` | то же самое, отдаёт файл `fmt=csv\|xlsx` |
| `GET /plan`, `GET /plan/export` | план выпуска вагонов на 1–7 дней, итог в вагоно-часах, XLSX для депо |
| `POST /decisions`, `GET /decisions` | журнал «принять / отклонить / отложить» по алертам |
| `GET /decisions/report` | решения и поступившее число посадок по дате и маршруту; не доказательство исполнения плана |

Приём данных: только даты после текущей даты данных; файлы сохраняются в том `ingest`, движок подхватывает их за ~1 минуту
и сдвигает горизонт.
Максимум 10 МБ на запрос; точный повтор пакета идемпотентен, пересекающиеся
маршрут-дата-час отклоняются, нечисловые и неизвестные маршруты отклоняются.
Отправитель должен передавать **полные дни**: сервис не может определить по
редкому потоку валидаций, что день ещё не завершён.

Пользователи, журнал решений диспетчера и журнал приёма данных хранятся в PostgreSQL
(контейнер `db` в `docker-compose.yml`, том `postgres`, подключение — `DATABASE_URL`).
Пароль базы по умолчанию — только для локального демо; перед внешним развёртыванием
задать `TRAM_DB_PASSWORD` и `AUTH_SECRET`. Прогноз и архив остаются Parquet на томе
`state` — БД не нужна на горячем пути чтения прогноза.

Пример (полный сценарий с авторизацией — [`../docs/JURY.md`](../docs/JURY.md)):

```bash
curl -H "Authorization: Bearer $TOKEN" "http://localhost:8123/forecast?date_from=2025-11-01&date_to=2025-11-07&route=17&granularity=day&coefficient=1.1"
```

Горизонт — 12 месяцев от даты последних данных (сейчас 01.11.2025 – 31.10.2026); запрос вне горизонта
получает 400 с понятным сообщением. В ответе `/forecast` есть `data_until` и `model_version`.
Ноябрь–декабрь 2025 совпадает с отправленным сабмитом (0,88960) до 0,0043 %.

Полная интерактивная документация (Swagger UI): http://localhost:8123/docs.

## Интерфейс

React-приложение (`web/src/`), сборка в образе `web` (nginx раздаёт статику и проксирует `/api/*` на API).
Разделы: **Обзор** (прогноз, коридор 80 %, нагрузка по маршрутам, состояние маршрутов), **Оперативная ситуация**
(текущий и следующие часы, рекомендации с кнопками «Принять / Позже / Отклонить»), **Карта и остановки** (MapLibre,
геометрия маршрутов из OpenStreetMap, оценочные посадки по остановкам), **Загрузка вагонов**, **План выпуска** (7 дней,
экспорт), **Качество прогноза** (прогноз против факта), **Журнал решений**. «Параметры» — период, маршруты, часы и
сценарный коэффициент; экспорт CSV / XLSX у каждой таблицы.

Геометрия справочника организаторов (`Порядок_с_координатами`) для карты не использована: `route_id` в нём — внутренняя
нумерация парка, не совпадающая с `ngpt_route` из данных валидаций; геометрия взята из OpenStreetMap по номеру маршрута.

## Производительность

4 vCPU / 4 ГБ, PostgreSQL, смешанный профиль диспетчера: при 200–400 RPS p95 6 мс, требование p95 ≤ 300 мс выдерживается
до ≈ 1 100–1 250 RPS, потолок ≈ 1 100–1 320 RPS (два прогона, разница — нагрев ноутбука), 0 ошибок. Во время пересчёта прогноза p95 на 4–5 с поднимается до ≈ 1,4 с.
Подробно — [`../docs/PERFORMANCE_AND_FEATURES.md`](../docs/PERFORMANCE_AND_FEATURES.md), все прогоны — [`../docs/TESTS.md`](../docs/TESTS.md) §5.
Повтор ступенчатого теста — `api/loadtest_steps.sh`; отчёты Locust — `api/loadtest_report/`.
Отдельный тест приёма фактов во время нагрузки и восстановления после сбоя — `api/ingest_load_proof.py`; методика и результаты — [`../docs/TESTS.md`](../docs/TESTS.md) §5.
