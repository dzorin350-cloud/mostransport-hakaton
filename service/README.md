# Веб-сервис: прогноз пассажиропотока трамваев Москвы

Backend + frontend поверх ML-модели v7 (WAPE-score 0.88399, см.
[../ARCHITECTURE.md](../ARCHITECTURE.md) и [../README.md](../README.md)).

Этот каталог закрывает требования ТЗ хакатона, которых не было в исходной
модели: REST/HTTP API, интерактивный дашборд с картой, экспорт в
CSV/XLSX, корректирующие коэффициенты в интерфейсе, замеры
производительности.

## Быстрый старт

```bash
cd service
docker compose up -d --build            # 4 vCPU / 4 ГБ RAM, 4 воркера (по умолчанию)
# минимальная конфигурация по ТЗ — 2 vCPU / 2 ГБ RAM, 2 воркера:
docker compose -f docker-compose.yml -f docker-compose.2cpu.yml up -d --build
```

- Дашборд: http://localhost:8080
- API: http://localhost:8123 (или http://localhost:8080/api/... через прокси nginx)
- Проверка: `curl http://localhost:8123/health`

Остановить: `docker compose down`.

## Архитектура

```
┌─────────────────────┐      ┌──────────────────────┐      ┌─────────────┐
│  v7/code/*.py        │      │  service/api          │      │ service/web │
│  (модель, отдельно,   │ ──►  │  FastAPI, читает       │ ◄──  │  дашборд,    │
│  см. корень репо)     │      │  предрассчитанный CSV  │      │  MapLibre,   │
│  прогон раз в неделю  │      │  в память при старте   │      │  Chart.js    │
└─────────────────────┘      └──────────────────────┘      └─────────────┘
```

**Почему прогноз предрассчитан, а не считается на лету.** ТЗ требует
сотни RPS при p95 < 200-300 мс на 2-4 vCPU. Инференс CatBoost (5 моделей)
на каждый HTTP-запрос не уложится в этот бюджет и не нужен: прогноз
меняется только при переобучении модели (раз в неделю или по приходу
новых данных валидаций — штатный режим, описанный в корневом README).
Между переобучениями сервис отдаёт готовую сетку из памяти — это и есть
≈ 610–885 RPS (в зависимости от 2 или 4 vCPU) и p95 190–280 мс, которые ниже
измерены нагрузочным тестом.

Корректирующие коэффициенты (погода/событие/сезон) применяются
**множителем поверх готового прогноза** — мультипликативная структура
модели (`уровень × форма дня × сезонный множитель`, см. ARCHITECTURE.md
§1) прямо это позволяет, без повторного инференса.

## API

| Эндпоинт | Что делает |
|---|---|
| `GET /health` | статус сервиса |
| `GET /metrics` | счётчики запросов, средняя латентность, версия модели |
| `GET /routes` | список маршрутов |
| `GET /routes/geometry` | GeoJSON геометрии 9 маршрутов (OpenStreetMap) |
| `GET /forecast` | прогноз с фильтрами: `date_from`, `date_to`, `route[]`, `hour_from/to`, `granularity=hour\|day\|month`, `coefficient` |
| `GET /forecast/export` | то же самое, отдаёт файл `fmt=csv\|xlsx` |

Пример:

```bash
curl "http://localhost:8123/forecast?date_from=2025-11-01&date_to=2025-11-07&route=17&granularity=day&coefficient=1.1"
```

Источник данных подбирается автоматически: запрос внутри ноября-декабря
2025 обслуживается точным сабмитом `v7/submission_v7.csv` (тем самым,
что дал 0.88399 на лидерборде), запрос на более широкий горизонт —
годовым прогнозом `forecast_year_2025-11_2026-10.csv`.

Полная интерактивная документация (Swagger UI): http://localhost:8123/docs.

## Дашборд

- **Карта** (MapLibre GL, тайлы OpenStreetMap без API-ключа): реальная
  геометрия 9 маршрутов, полученная через Overpass API
  (`relation[route=tram][ref=...]` по каждому маршруту, лицензия
  ODbL/CC-BY-SA). Цвет линии — относительная загрузка маршрута за
  выбранный период (зелёный/жёлтый/красный).
- **Три горизонта** (кнопки День / Месяц / Год) — критерий ТЗ п.4.
- **Фильтр по маршрутам** — клик по чипу слева.
- **Корректирующие коэффициенты**: слайдер ×0.5…×1.5 плюс пресеты
  «Дождь» (×0.85) / «Событие» (×1.15) / «Норма» — критерий ТЗ п.2в,
  результат виден мгновенно без перезагрузки страницы.
- **Экспорт CSV/XLSX** — кнопки внизу правой панели.
- KPI: сумма посадок за период, число активных маршрутов, пиковый час/день,
  latency p95 из нагрузочного теста (4 vCPU / 4 воркера).

Геометрия справочника `Хакатон_справочники_трамвай_10_маршрутов.xlsx`
(`Порядок_с_координатами`) для карты **не использована**: `route_id` в
нём — внутренняя нумерация парка подвижного состава, не совпадающая с
`ngpt_route` из train.csv/test.csv (проверено построчно: в справочнике
`route_short_name="5"` — это маршрут Рижская—Белорусский вокзал, тогда
как в данных валидаций маршрут 5 пуст). Прямой связки между двумя
системами нумерации в датасете нет, поэтому для карты взята независимая
и верифицируемая геометрия из OpenStreetMap по номеру маршрута.

## Производительность

ТЗ допускает контейнер 2–4 vCPU / 2–4 ГБ RAM, поэтому замерены обе границы.
Число воркеров uvicorn равно числу vCPU и задаётся переменной `WORKERS`
(по умолчанию 4; для 2 vCPU — `docker-compose.2cpu.yml`). Замеры —
`api/loadtest.py` (Locust), сценарий одинаковый во всех прогонах:

```bash
cd service/api
locust -f loadtest.py --host http://127.0.0.1:8123 \
    --headless -u 200 -r 40 -t 30s --csv=loadtest_report
```

Стенд: MacBook Air (Apple M5), Docker Desktop (10 ядер, 8 ГБ), Locust на той же
машине; 30 с на прогон, во всех прогонах **0 ошибок**.

| Конфигурация контейнера | Пользователей | RPS | p50, мс | p95, мс | p99, мс | CPU контейнера | Память |
|---|---|---|---|---|---|---|---|
| **2 vCPU / 2 ГБ, 2 воркера** | 100 | 598 | 21 | 90 | 130 | — | — |
| **2 vCPU / 2 ГБ, 2 воркера** | 200 | **≈ 610** | 160 | **280** | 330 | 195 % из 200 % | 310 МБ |
| 4 vCPU / 4 ГБ, 2 воркера (для сравнения) | 200 | 689 | 140 | 250 | 340 | 220 % из 400 % | 302 МБ |
| **4 vCPU / 4 ГБ, 4 воркера** | 200 | **≈ 885** | 77 | **190** | 250 | 404 % из 400 % | 521 МБ |
| **4 vCPU / 4 ГБ, 4 воркера** | 400 | 879 | 280 | 440 | 520 | 405 % из 400 % | 582 МБ |

Выводы:

- **Потолок упирается в процессор:** при 4 воркерах CPU контейнера 404 % из 400 %, удвоение
  нагрузки (400 пользователей) не увеличивает RPS (≈ 880), растёт только задержка.
- **Лимит vCPU без увеличения воркеров ничего не даёт:** при лимите 4 vCPU и 2 воркерах RPS
  вырос лишь с 610 до 689, потому что 2 воркера используют около 2,2 ядра.
- Оба режима укладываются в требование ТЗ (сотни RPS, p95 < 200–300 мс на 2–4 vCPU).
  Ранее заявленные здесь 849 RPS / p95 180 мс соответствуют конфигурации 4 vCPU / 4 воркера.

Отчёты Locust: [`api/loadtest_report/`](api/loadtest_report/) (`loadtest_<vCPU>_<воркеры>_<пользователи>u_stats.csv`).
Профиль нагрузки — смесь запросов: почасовой прогноз на 1 маршрут/1 день (основной
паттерн дашборда), суточная агрегация на весь горизонт, запросы с
коэффициентом, health-check.

**На single-worker (без `--workers`)** тот же тест давал p95 690 мс —
цифра из первого прогона, оставлена для сравнения при отладке: узкое
место — GIL при синхронном pandas-фильтре, снимается несколькими
воркерами uvicorn (по числу vCPU, переменная `WORKERS` в Dockerfile).

## Область применимости (дополнение к ARCHITECTURE.md §8)

- API отдаёт то, что уже предсказано моделью — сам сервис не переобучается
  и не валидирует бизнес-осмысленность коэффициента (например, `×3.0`
  физически бессмысленно, но API его не отклонит за пределами диапазона
  `(0, 3]`, заданного как защита от опечатки, не как доменное ограничение).
- Геометрия карты — база OSM на момент выгрузки (сентябрь 2026); при
  изменении трассы маршрута в реальности карта не обновится без повторного
  запроса к Overpass API.
- Для прогноза за пределами ноября 2025 — октября 2026 нужен новый прогон
  `v7/code/forecast.py` с расширенным горизонтом (ограничение модели: до
  12 месяцев от конца обучающих данных, см. ARCHITECTURE.md §6).
