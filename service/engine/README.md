# Движок прогноза

Сервис сам применяет модель: API больше не читает готовые CSV-прогнозы.

## Как работает

```
история валидаций (HISTORY_DIR, route;date;hour;boardings)
        │                                  ┌── isdayoff.ru: производственный календарь (live → кэш → встроенная копия)
        ▼                                  ├── data.mos.ru 62521: месячный пассажиропоток трамвая,
  refresher.py (фоновый процесс) ◄─────────┘   только месяцы ≤ даты данных (live → кэш → встроенная копия)
        │  core.Engine.refresh():
        │   1. сетка маршрут × дата × час, дата последних данных
        │   2. очистка от перекрытий и сбоев (как v7)
        │   3. уровень маршрута (56 дней), профиль (2 недели)
        │   4. 5 моделей CatBoost (artifacts/, обучены офлайн)
        │   5. сезонный множитель месяца (city data), горизонт 12 месяцев
        │   6. годовая часть: форма дня «тот же месяц год назад» (доля 0,5)
        ▼
  STATE_DIR/versions/<id>/forecast.parquet + info.json → current.json (атомарный указатель)
        │
        ▼
  API-воркеры (uvicorn): держат прогноз в памяти, перечитывают новую версию (проверка раз в 30 с)
```

Пересчёт запускается при старте контейнера, при изменении файлов в `HISTORY_DIR` (проверка раз в `CHECK_SECONDS`)
и раз в `REFRESH_HOURS` (заново скачиваются календарь и сезонность). Если пересчёт падает, остаётся прошлый прогноз.

Модели CatBoost в сервисе не обучаются: `python -m service.engine.train` (из корня репозитория) обучает их кодом v7
и сохраняет в `artifacts/`.

## Файлы
| Файл | Что делает |
|---|---|
| `core.py` | движок: календарь, очистка, применение модели, множители, годовая форма дня |
| `sources.py` | загрузка внешних данных с жёстким лимитом времени и цепочкой live → кэш → встроенная копия |
| `refresher.py` | фоновый процесс пересчёта и публикации |
| `train.py` | офлайн-обучение 5 моделей CatBoost (код v7) → `artifacts/` |
| `artifacts/` | модели `catboost_seed*.cbm`, `config.json` (параметры, маршруты, версия) |
| `fallback/` | встроенные копии внешних данных на случай недоступности источников |

## Приём новых данных
`POST /ingest/validations` и `POST /ingest/hourly` (API, с авторизацией) сохраняют почасовые агрегаты в `INGEST_DIR`
(том Docker). Движок читает историю из `HISTORY_DIR` и `INGEST_DIR` вместе, замечает новый файл и пересчитывает прогноз;
база сезонных множителей — последний месяц, по которому есть городская статистика (при неполном текущем месяце — прошлый).
Статус последнего пересчёта (успех или ошибка) — `last_refresh` в `/model/info`.
Городская статистика и база сезонных множителей — последний **полный** месяц истории (при неполном текущем месяце — прошлый),
чтобы в месячный итог не попадали дни, которых у модели ещё нет.
Каждая опубликованная версия прогноза сохраняется в `STATE_DIR/archive/forecast_until_<дата данных>.parquet`;
`GET /monitor/accuracy` сравнивает поступившие факты с прогнозом из архива, сделанным до них (`forecast=latest|earliest`).

## Погода и остановки
- **Прогноз погоды** (Open-Meteo, 16 дней) скачивается при каждом пересчёте; в дни с 3+ дневными сроками осадков прогноз посадок × 0,975
  (`RAIN_EFFECT`). Дни с поправкой — `rain_adjusted_days` в `/model/info`.
- `WEATHER_MODE=forecast` (по умолчанию, прод) — прогноз погоды; `WEATHER_MODE=demo` — **только для демонстрации** на стенде со старыми
  данными: фактическая погода из архива за первые 16 дней горизонта (в `docker-compose.yml` стенда включён demo). На сабмит не влияет.
- **Остановки:** `python -m service.engine.build_stops <каталог CSV data.mos.ru>` строит `artifacts/stops.csv` (доли остановок в прогнозе
  маршрута) и `artifacts/stops.geojson`; API `/stops`, `/forecast/stops`.

## Переменные окружения
| Переменная | По умолчанию | |
|---|---|---|
| `HISTORY_DIR` | `/app/history` | история валидаций (монтируется томом, пополняется) |
| `STATE_DIR` / `OUT_DIR` | `/app/state` | куда публикуется прогноз |
| `INGEST_DIR` | `/app/ingest` | данные, принятые через API (том `ingest`) |
| `AUTH_DIR` | `/app/auth` | пользователи SQLite и секрет токенов (том `auth`); `AUTH_SECRET` — задать секрет явно |
| `REFRESH_HOURS` | 24 | плановый пересчёт |
| `CHECK_SECONDS` | 60 | как часто проверять новые файлы истории |
| `WORKERS` | 4 | воркеры API (= числу vCPU) |

## API
- `GET /model/info` — как построен текущий прогноз: дата данных, горизонт, множители месяцев, месяцы с годовой формой,
  источники внешних данных (`live` / `cache` / `fallback`), время расчёта.
- `GET /forecast?date_from&date_to&...&granularity=hour|day|week|month` — любой диапазон внутри горизонта
  (12 месяцев от даты данных); вне горизонта — 400 с понятным сообщением. В ответе `data_until`, `model_version`.

## Проверено (26.09.2026, Docker, 4 vCPU / 4 ГБ)
- Ноябрь–декабрь 2025 совпадает с отправленным `submission_v7.csv` до 0,0023 % (297 посадок на 12,8 млн;
  причина — праздничные блоки считаются по календарю isdayoff, а не по ручному списку v7: 8–9 марта 2025).
  v7, переобученная с календарём isdayoff, на лидерборде дала те же 0,88399 (`docs/TESTS.md` §3).
- Любые диапазоны; суммы согласованы (час = день = неделя = месяц).
- Новые данные: после появления файла с октябрём в истории (старт с данными до 30.09) через 33 с все воркеры
  отдают прогноз с новой датой данных и сдвинутым горизонтом, без перезапуска.
- Пересчёт прогноза на 12 месяцев: ≈ 4,5 с расчёта + загрузка внешних данных (до 21 с, если data.mos.ru не отвечает).
- Нагрузка (Locust, 200 пользователей): 1 282 RPS, p95 68 мс на 4 vCPU; 890 RPS на 2 vCPU; 0 ошибок.
- Ограничение: data.mos.ru с тестовой машины недоступен (сайт закрыт для зарубежных адресов), поэтому сезонность в
  тестах бралась из встроенной копии; в российском контуре она будет скачиваться. Календарь isdayoff.ru — live.
